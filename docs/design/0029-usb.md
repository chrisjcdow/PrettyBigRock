# 0029: USB: the EHCI driver, hubs, `pbr.usb` and devices that come and go

Status: Accepted · 25 November 2026, accepted 26 November 2026 · Related: DESIGN.md sections 7.1 and 8; notes 0010, 0011,
0012, 0018, 0027, 0028; `docs/m7-plan.md` (Q3, Q8, Q13); milestone M7

## The problem

Roxy's keyboard, mouse and the stick it boots from are all USB devices. Until now every device
PrettyBigRock drives has been found once, at start, on PCI or in a short list; USB devices are
found *through* another device, may be plugged in behind hubs, and come and go while the
system runs.

USB in brief, for a reader new to it:
- A **host controller** (a PCI device) runs the bus. It reads lists of work, **schedules**, from
  memory by DMA (note 0010, section 6), and writes the results back. EHCI is the USB 2 kind
  of controller; Roxy has two (`00:1a.0` and `00:1d.0`), each with its interrupt on a shared
  line (16 and 23), and no MSI.
- A bus has up to 127 **devices**, each given an address. A device talks through
  **endpoints**: endpoint 0 for **control** requests (questions and settings, each starting with
  an 8-byte *setup packet*), and others for **bulk** data (a stick's sectors), **interrupt**
  data (a keyboard's reports, collected by the controller asking every few milliseconds) or
  **isochronous** data (audio, not in M7).
- A device describes itself with **descriptors**: a device descriptor (who made it, what it
  is), one or more configurations, and in each, **interfaces** with their endpoints. A
  keyboard with media keys may have two interfaces; a stick has one. Each interface is a
  separate function and is what a **class driver** (keyboard, mouse, storage) drives.
- **Hubs** are devices with ports. Every port on Roxy's back panel is behind a hub: each EHCI
  controller has one port, wired to a hub built into the chipset (a **rate-matching hub**).
  Keyboards and mice are *low-speed* or *full-speed* (USB 1.1) devices, and a USB 2 controller
  reaches them only through a hub's **transaction translator**, which turns the controller's
  fast messages into slow ones: **split transactions**. So on Roxy, hubs and split
  transactions are needed before the first key press.
- Until the operating system takes over, the firmware drives the controllers itself and
  pretends USB keyboards are PS/2 ones (**legacy emulation**), using system management mode,
  a part of the processor the operating system can't see.

This note settles:
- how USB is split into programs (Q3), and what each may touch;
- how the controllers are taken from the firmware;
- the EHCI driver: its schedules, DMA, split transactions, hubs and finding devices;
- `pbr.usb`, the class drivers' view of one interface, and the rules it enforces;
- how the device manager starts and stops class drivers as devices come and go, and how its
  clients hear about it (note 0011's open question on hot-plug), with a stable identity for
  each device.

Keyboards, mice and storage themselves are note 0030.

## The design

### 1. The parts

```
 devmgr ──starts──▶ drivers/ehci (one per controller: its registers, DMA, line, every hub)
   ▲                    │
   │ pbr.usb.host       │ pbr.usb, one badge per interface
   │ (what's plugged in)▼
   └──starts──▶ class drivers (usb-hid, usb-storage: note 0030), one per interface
                    │
                    └──▶ pbr.input, pbr.block ──▶ the input and storage services
```

- **`drivers/ehci`**, the **host driver**: one process per controller, started by the device
  manager as any PCI driver is. It owns the controller's registers, its DMA memory and its
  interrupt line, drives **every hub** on its bus (the controller's own ports, the
  rate-matching hub and any hub plugged in), gives each device an address and reads its
  descriptors. It doesn't drive keyboards or sticks; it tells the device manager about each
  interface it finds, and serves `pbr.usb` to whichever class driver the device manager starts
  for it.
- **Class drivers**, one process per interface (Q3), started by the device manager from
  manifests like any driver's. A class driver gets **no device capabilities at all**: no
  registers, no DMA, no interrupts. It gets one capability, to its interface on the host
  driver. Everything a device says beyond the basic descriptors (a keyboard's report
  descriptor, a stick's answers to SCSI commands) is parsed there, by a program that can't
  program DMA or reach any other device.
- **`lib/usb`** (`pbr-usb`, GPL-3.0-or-later, `no_std` with `alloc`): what the host driver
  knows about USB that can be tested away from hardware: descriptors and setup packets,
  the EHCI data structures and how they are encoded, the schedule's planning, and the hub and
  finding-devices logic as state machines (section 10). Class drivers use its descriptor code
  too.

**Why hubs are in the host driver**, not in a hub class driver of their own: finding a device
behind a hub needs the bus's address 0 (only one new device may use it at a time, across all
hubs), the controller's address allocation, and the hub's transaction translator details in
the controller's schedule. A separate hub driver would need a privileged interface to all
three, and the hub protocol is small. The cost is that the host driver, which has DMA, parses
hub and device descriptors: small fixed formats, in `lib/usb`, tested with hostile inputs.

### 2. Taking the controllers from the firmware

An EHCI controller has a **legacy support** register pair in its PCI configuration space, at
the offset its `HCCPARAMS` register gives (`EECP`, bits 8 to 15), where the firmware and the
operating system hand it over: the operating system sets "OS owned" (bit 24) and waits for the
firmware to clear "BIOS owned" (bit 16), then turns off the firmware's system management
interrupts for it (the register after).

**The device manager does this**, during its PCI scan, for every EHCI function (class `0C`,
sub-class `03`, interface `20`), **before it switches the functions off** (note 0018,
section 4) and before any driver starts. It reads `HCCPARAMS` through a one-page mapping of
the controller's registers (BAR 0), then works in configuration space it already holds. It
waits up to one second for the firmware to let go; if the firmware doesn't, it logs that,
turns the interrupts off anyway, and carries on, as Linux does.

Doing it there, not in the EHCI driver:
- the firmware must stop touching the controller *before* the device manager turns its memory
  and bus mastering off, or the firmware's hidden code may hang the machine on a controller
  that no longer answers;
- the PS/2 driver must not start while the firmware is still pretending to be a PS/2
  controller in front of it: Linux takes USB controllers from the firmware first for the same
  reason;
- it happens once per device manager start, whether or not a driver for the controller exists.

**What this means for the keyboard.** A USB keyboard works through the firmware's emulation
until the device manager starts, then not at all until the keyboard's class driver is
running: a few seconds during start-up in which nothing reads keys. On Roxy the firmware's
emulation is the only reason the keyboard works in the loaders' menus; once the kernel runs,
nothing needs it.

### 3. The host driver

**Starting.** Like every driver it starts from reset (note 0011, section 7): it stops the
controller (clears Run/Stop and waits up to 20 ms for "halted"), resets it (waits up to 250 ms),
then builds its schedules, routes every port to itself (`CONFIGFLAG`), powers the ports, and
starts. Controllers with **companion controllers** (the USB 1.1 controllers that older
chipsets put beside EHCI for slow devices, `N_CC` in `HCSPARAMS`) aren't supported in M7: the
driver still drives the high-speed devices, and logs a slow device on a root port as needing a
companion. Roxy and QEMU's `ich9-usb-ehci1` have none.

**DMA memory.** The manifest asks for 1 MiB **below 4 GiB**, which lets every structure and
buffer use 32-bit addresses whether or not the controller can do 64-bit (`HCCPARAMS` bit 0),
so the segment register is always 0. Manifests gain a word for this, `dma 1M low` (note 0011,
section 5, changes; the device manager passes `memory_create_dma`'s `BELOW_4G` flag, note
0010). Note 0011 left a DMA allocator to "the first driver that needs one", which this is:
`lib/usb` has two simple ones over the driver's DMA memory, both host-tested:
- a **slot pool** of 64-byte slots for the controller's queue heads and transfer descriptors
  (aligned to 32 bytes, as EHCI needs), 64 KiB of them;
- a **page pool** of 4 KiB pages for data, a transfer taking as many as it needs (16 for the
  largest, 64 KiB).

The first 4 KiB is the **frame list** (below). All the rest is pages: room for a dozen 64 KiB
transfers at once, more than a few devices need. A transfer that can't get memory waits for
another to finish.

**The schedules.** EHCI works from two lists in memory:
- the **asynchronous schedule**, a circle of *queue heads* (one per control or bulk endpoint
  in use, plus a fixed head of the list), each with a chain of *transfer descriptors* (each
  describing up to 20 KiB of one transfer). The controller goes round it whenever the bus is
  free. Control and bulk transfers go here.
- the **periodic schedule**: the frame list's 1024 entries, one per millisecond, each pointing
  at the queue heads to visit in that millisecond. An interrupt endpoint's queue head is linked
  into every *n*th entry, where *n* is its polling interval rounded down to a power of two from
  1 to 32 ms, starting at the entry that keeps the busiest millisecond least busy. Longer
  intervals come first in each entry's chain, so chains share their tails. A high-speed
  endpoint asking to be polled more often than once a millisecond is polled once a
  millisecond, which is ample for keyboards and mice.

**Taking a queue head out safely.** The controller may still be reading a queue head just
removed from a list, so its memory isn't reused until the controller has certainly moved on:
for the asynchronous schedule, until the controller answers the **async advance doorbell**
(`USBCMD` bit 6, then `USBSTS` bit 5); for the periodic schedule, until two milliseconds
have passed on the controller's frame counter. This is the rule most likely to be broken by a
change, so `lib/usb`'s pools enforce it: a slot is freed "after the doorbell" or "after frame
F", never directly.

**Split transactions.** A low- or full-speed device behind a high-speed hub is reached through
that hub's transaction translator. Its queue heads carry the hub's address and port (the
nearest high-speed hub on the way to the device, and the port leading to it), and, for
control endpoints, EHCI's "control endpoint" flag. For the asynchronous schedule the
controller does the rest. For interrupt endpoints the driver also says in which of a
millisecond's eight *microframes* to start the transaction (`S-mask`) and in which to collect
the answer (`C-mask`): start in microframe 0 to 3, chosen like the starting entry above, and
complete in the three microframes two to four later, as the USB 2 specification's simple
case allows. There is no full bandwidth accounting in M7: a periodic entry with more than 16
endpoints refuses another, logged. If a split control or bulk transfer fails, the driver sends
the hub `CLEAR_TT_BUFFER` before the endpoint is used again, so a half-finished transaction
in the translator can't confuse the next one.

**Finishing transfers.** The controller marks each transfer descriptor done (or halted, with a
reason: stalled, babble, a bus error after three tries, a buffer problem). The driver checks
every value it reads back: a length the controller says it moved that is longer than the
transfer, or a pointer outside the driver's memory, fails that transfer as a device error.
An interrupt (`USBINT`, `USBERRINT`, port change, async advance, host system error) makes the
driver look at every active transfer; it doesn't trust the interrupt to say which. A **host
system error** (the controller couldn't reach memory) stops the controller, so the driver
logs it and ends, and the device manager restarts it.

**The interrupt line.** A shared, level-triggered line (note 0027, section 2): the driver
clears the status bits it handled, writing them back, then acknowledges the line.

**Timers.** Hubs need waits (100 ms for a new connection to settle, 50 ms of reset), and
transfers need time limits. `lib/driver`'s event loop waits for ever today; it gains a
`next_wake` and a `wake` in its `Service` trait (both optional, as `gone` is), so the loop
waits until the earliest deadline and the driver never sleeps inside a handler. The whole
driver is single-threaded and never blocks: finding a device is a series of steps, each
started by a completion or a timer.

### 4. Hubs and finding devices

**Ports.** The controller's own ports (the **root hub**) and every external hub's ports are
treated alike through a `Hub` trait in `lib/usb`: "port status", "set or clear a port
feature", "status changed". For the root hub it reads and writes `PORTSC`; for an external hub,
it sends hub class requests on endpoint 0, and learns of changes from the hub's interrupt
endpoint, which the periodic schedule polls.

**A device appears.** When a port says something connected:
1. wait until the connection has been steady for **100 ms** (a plug is jittery going in);
2. **reset the port**: 50 ms on a root port, 20 ms on a hub's port; then wait 10 ms more. On
   a root port, a port that isn't enabled after reset holds a slow device that needs a
   companion controller (section 3): logged and left. On a hub, the port's status says the
   device's speed;
3. take the bus's **address 0** (one device at a time across the bus; the others wait), and
   read the first 8 bytes of its device descriptor, which say how big endpoint 0's packets are;
4. give it an address (the lowest free from 1 to 127) with `SET_ADDRESS`, wait 2 ms, and let
   address 0 go;
5. read the whole device descriptor (18 bytes), then the first configuration's descriptors
   (at most 16 KiB; a device saying more is refused), and its **strings**: maker, product
   and serial number, in US English if it offers that, otherwise its first language, each cut
   to 64 bytes of UTF-8 with control characters replaced;
6. `SET_CONFIGURATION` with the **first** configuration. Almost every device has only one;
   choosing among several is an open question;
7. if it is a hub: read its hub descriptor, power its ports, wait as long as it says power
   takes to settle, and watch its ports. If it isn't: tell the device manager about each
   interface (alternate setting 0) through `pbr.usb.host` (section 6).

A device that fails a step (no answer within 5 s, a stall, nonsense) is tried again from step 2,
three times in all, then its port is disabled and logged: "the device on port 1.3 doesn't
answer".

**Limits.** 127 addresses per controller; hubs at most **five deep** below the root hub, as
the USB specification allows (a sixth is refused); a hub with at most 15 ports; at most 32
interfaces per device; descriptors are checked as `lib/devices` checks configuration space
(note 0011, section 3): every length and count is checked against what's there before it is
used, and a descriptor that doesn't fit is an error, never an overrun.

**A device goes.** When a port says the connection went (or a device stops answering
altogether), the driver ends every transfer for it with `Gone`, takes its queue heads out
(section 3's rules), cuts off its class drivers' capabilities (section 5), and tells the device
manager each interface has gone. A hub going takes everything below it, deepest first. The
address is free again once its queue heads are.

**Over-current**: a port reporting it is turned off and logged; its device is gone.

### 5. The class drivers' view: `pbr.usb`

```
/// One interface of a USB device, as its class driver sees it.
interface pbr.usb version 1;

flexible enum Speed { Low @1, Full @2, High @3 }

/// A control request's setup packet, as the USB specification lays it out.
struct Setup { request_type: u8, request: u8, value: u16, index: u16, length: u16 }

/// The device's speed, its device descriptor, and this interface's descriptors: from its
/// interface descriptor up to the next interface's, so including its endpoints and any
/// class-specific descriptors (a keyboard's HID descriptor).
@1 fn describe() -> (speed: Speed, device: bytes<18>, interface: bytes<4096>) error UsbError;

/// A control transfer on endpoint 0. `data` is sent if the request is host-to-device; the
/// answer holds what the device sent otherwise. At most `setup.length`, at most 4096 bytes.
@2 fn control(setup: Setup, data: bytes<4096>, timeout_ms: u32)
    -> (data: bytes<4096>) error UsbError;

/// Sends `data` on a bulk OUT endpoint of this interface.
@3 fn bulk_out(endpoint: u8, data: bytes<65536>, timeout_ms: u32) -> (sent: u32) error UsbError;
/// Receives up to `max` bytes (at most 65536) from a bulk IN endpoint of this interface.
@4 fn bulk_in(endpoint: u8, max: u32, timeout_ms: u32) -> (data: bytes<65536>) error UsbError;

/// Waits for the next report from an interrupt IN endpoint of this interface: answers when the
/// device sends one, however long that takes.
@5 fn interrupt_in(endpoint: u8) -> (data: bytes<1024>) error UsbError;
/// Sends a report on an interrupt OUT endpoint (a keyboard's lights, on some keyboards).
@6 fn interrupt_out(endpoint: u8, data: bytes<1024>, timeout_ms: u32) -> () error UsbError;

/// Clears a halted endpoint of this interface (`CLEAR_FEATURE(ENDPOINT_HALT)`), resetting
/// the host's side of it too.
@7 fn clear_halt(endpoint: u8) -> () error UsbError;

flexible enum UsbError {
    /// The device was unplugged, or this capability was cut off.
    Gone @1,
    /// The device refused (a STALL); for bulk and interrupt endpoints, `clear_halt` before
    /// trying again.
    Stalled @2,
    /// No answer within the time limit.
    TimedOut @3,
    /// The device answered badly (a bus error, babble, too much data).
    DeviceError @4,
    /// Not this interface's to ask (section 5's rules).
    NotAllowed @5,
    /// A bad endpoint, length or request.
    BadArgument @6,
    /// A transfer on that endpoint is already under way.
    Busy @7,
}
```

**Copying, not sharing.** Data travels in the calls' attached buffers, and the host driver
copies it to and from its DMA memory. So class drivers never see a bus address, and no class
driver's mistake can make the controller write somewhere it shouldn't. Copying 64 KiB costs
far less than a USB 2 bus takes to move it (EHCI manages about 30 to 40 MB/s in practice).

**One transfer per endpoint at a time**, which is all keyboards, mice and storage (one
command, its data, its status) need, and keeps the driver simple. `interrupt_in` answers only
when a report comes: the class driver keeps one waiting, and the host driver polls the
endpoint only while one is. A report the device has while no call is waiting stays in the
device until the next poll, so nothing is lost.

**What the host driver allows.** Each class driver's capability carries a badge (note 0008)
that the host driver knows as "interface *i* of device *d*". Then:
- **endpoints** must be this interface's, in the right direction and of the right type;
- **control requests** are allowed to the interface itself (the recipient is "interface" and
  the low byte of `index` is its number) and to its own endpoints, of any kind, standard,
  class or vendor; but the standard requests that change the device or the interface
  (`SET_ADDRESS`, `SET_CONFIGURATION`, `SET_INTERFACE`, and `SET_FEATURE` or `CLEAR_FEATURE`
  on the device) are refused, and `CLEAR_FEATURE(ENDPOINT_HALT)` must go through `clear_halt`
  so both sides stay in step;
- **to the device as a whole**, only reading: `GET_DESCRIPTOR` and `GET_STATUS`. Class and
  vendor requests to the device are refused in M7: they could reach a composite device's
  other interfaces. A driver that needs one is an open question.

So a hostile or broken class driver can reach only its own interface: not the device's other
interfaces, not other devices, not the hubs.

### 6. Between the host driver and the device manager: `pbr.usb.host`

The host driver serves this on the endpoint it gives the device manager when ready (note
0011's `pbr.driver.host.ready`); the device manager never hands that endpoint to anyone else.
Calls go one way only, device manager to host driver, so the two can never wait on each other.

```
/// What a USB host driver tells its device manager.
interface pbr.usb.host version 1;

flexible enum Speed { Low @1, Full @2, High @3 }

/// One interface of a device that is plugged in.
struct Interface {
    /// The host driver's number for it. Never reused while the host driver runs.
    child: u32,
    /// From the device descriptor.
    vendor: u16, product: u16, release: u16,
    /// From the interface descriptor.
    class: u8, subclass: u8, protocol: u8, number: u8,
    speed: Speed,
    /// Where it is plugged in (section 7).
    path: string<48>,
    /// The device's strings (section 4), empty if it has none.
    maker: string<64>, name: string<64>, serial: string<64>,
}

flexible enum ChangeKind { Added @1, Removed @2 }
struct Change { kind: ChangeKind, interface: Interface }

/// Signals `bits` on `note` whenever there are changes to collect. Replaces any earlier watch.
@1 fn watch(note: handle<notification>, bits: u64) -> () error UsbHostError;
/// The changes since the last call, oldest first; `more` if there are others still.
@2 fn changes() -> (changes: list<Change, 8>, more: bool) error UsbHostError;
/// A new capability for a class driver to reach this interface through `pbr.usb`. Any
/// capability given out for it before is cut off, and its transfers ended.
@3 fn open(child: u32) -> (service: handle<any>) error UsbHostError;

flexible enum UsbHostError { NoSuchInterface @1 }
```

**The device manager**, for a driver whose manifest says it is a bus driver (`bus usb`, note
0011, section 5, changes), calls `watch` once it's ready, and on each signal collects the
changes:
- **Added**: it matches the interface against the manifests' new lines,
  **`match usb VVVV:PPPP`** (the device's vendor and product) and **`match usb class
  CC[:SS[:PP]]`** (the interface's class, sub-class and protocol), exact IDs first as for PCI.
  If one fits, it calls `open` and starts that class driver with the capability at a new
  role, **1060**, and a device record of a new kind, **4, USB interface** (vendor and product
  at offsets 8 and 10, class, sub-class and protocol at 12 to 14, the speed at 18 and the
  interface number at 19). A class driver's manifest may not ask for DMA or interrupts. If none
  fits, the interface is listed as **unclaimed** (section 7).
- **Removed**: it stops the class driver, if any, and takes the interface off its list.

**Restarts** (note 0012):
- **A class driver crashes**: the device manager restarts it as any driver, calling `open`
  again for a fresh capability; the host driver cuts off the old one and ends its transfers.
  The kernel tells the host driver when every capability with a badge has gone (note 0013),
  which ends a dead driver's waiting `interrupt_in` too.
- **The host driver crashes**: the controller has to be reset, and a reset forgets every
  device's address and configuration, so the new host driver must find the devices again from
  the start. But **the rest of the system needn't notice**, apart from a pause of a second or
  two. This matters most for the stick the system started from: if it looked unplugged, saving
  would stop until a restart (the plan's Q14).
  1. The device manager switches the controller off and starts the host driver again (note
     0012, section 2). It **keeps the class drivers running**, and their entries in the list,
     marked `Restarting`, with the same ids.
  2. The class drivers' calls fail (the old host driver's endpoint has gone). Each asks the
     device manager for its interface again, with a new operation in `pbr.driver.host`:
     ```
     /// For a class driver whose interface's capability stopped working: answers with a new one
     /// once the interface has been found again, or `Gone` if it isn't found within 10 seconds.
     @2 fn reconnect() -> (service: handle<any>) error HostError;
     ```
     (`HostError` gains `Gone @2`.) A class driver whose interface is gone ends, and the
     device manager takes it off the list.
  3. As the new host driver reports interfaces, the device manager pairs each with a waiting
     one from before when the path, vendor, product, interface number and class, and serial
     number (empty or not) all match. A pair gets a fresh capability (`open`), handed to the
     waiting `reconnect`. Anything unpaired after 10 seconds is treated as gone (the old) or new
     (the new).
  4. The class driver sets its device up again, since the reset undid its settings, and
     repeats the request that failed. Block reads and writes may be repeated safely (note
     0011, section 8); note 0030 says what each class driver does, including releasing keys a
     keyboard was holding down.

  The input and storage services keep their capabilities to the class drivers, which never
  stopped, so they see only a slow answer. If two identical devices without serial numbers
  swapped sockets during those seconds, each would be taken for the other, which is harmless.
- **A class driver crashes while its host driver is restarting**: the device manager starts it
  again once its interface has been found again, or not at all if it is gone.
- **The device manager restarts** (note 0018): everything starts again, as today.

### 7. Devices that come and go: `pbr.devices` version 2

The device manager's clients (the input, storage, display and console services) today read the
list once a second or once at start. With USB, devices come and go, the list can be longer
than 64, and a device needs a name that is the same tomorrow. `pbr.devices` goes to
**version 2**, replacing version 1 (every client is ours and changes in the same stage):

```
interface pbr.devices version 2;

flexible enum DeviceClass { Block @1, Input @2, Serial @3, Display @4, UsbHost @5, None @6 }
flexible enum DeviceState { Starting @1, Running @2, Restarting @3, Disabled @4, Unclaimed @5 }

struct DeviceInfo {
    /// Never reused while this device manager runs.
    id: u32,
    /// `None` for an unclaimed device.
    kind: DeviceClass,
    state: DeviceState,
    /// The driver's name, or for an unclaimed device what it is ("usb 0627:0001").
    name: string<48>,
    restarts: u32,
    /// The device it was found through (the USB host driver's), or 0.
    parent: u32,
    /// Where it is (below).
    path: string<64>,
    /// What it calls itself: a USB device's maker and product strings, or empty.
    product: string<64>,
    /// A USB device's serial number, or empty.
    serial: string<64>,
}

/// The devices, from `first` (0 to start); `next` is where to continue, if there are more.
@1 fn list(first: u32) -> (devices: list<DeviceInfo, 16>, next: option<u32>) error DevicesError;
/// As in version 1. A device that has gone is `NoSuchDevice`.
@2 fn open(id: u32) -> (service: handle<any>) error DevicesError;
/// Signals `bits` on `note` whenever the list changes: a device added or gone, or a driver's
/// state changed. Replaces any earlier watch from this client.
@3 fn watch(note: handle<notification>, bits: u64) -> () error DevicesError;

flexible enum DevicesError { NoSuchDevice @1, NotReady @2, Disabled @3, NotAllowed @4 }
```

`open` on a USB host driver is `NotAllowed`: only the device manager talks to it.

**Paths** say where a device is, in a form that stays the same across boots as long as nothing
is moved:
- PCI: `pci 0000:00:1d.0` (segment, bus, device, function);
- from ACPI (note 0028): `acpi \_SB.PCI0.LPCB.UAR2`;
- the boot framebuffer: `framebuffer 0`;
- USB: the controller's PCI address, the port at each hub tier from the root, and the
  interface: `usb 0000:00:1d.0-1.3:0` is interface 0 of the device on port 3 of the hub on the
  controller's port 1. (On Roxy every device is behind the rate-matching hub on port 1.)

A path together with a serial number is the **stable identity** of a USB device: the serial
says which stick, the path which socket. Note 0030 uses them to recognise a stick plugged in
again, and the storage service's "same number after a device manager restart" rule (note 0015)
becomes "same path and serial".

**The clients** each call `watch` and look again when signalled, instead of looking once a
second (input) or once at start (storage, display, console); a device gone from the list is
closed. They keep a slow look (every 10 s) in case a signal is missed while the device manager
restarts.

### 8. Distrusting devices and drivers

- **A hostile device** (a stick made to attack the machine) can lie in any descriptor or
  answer. The host driver parses only the device, configuration, string and hub descriptors,
  in `lib/usb`, checked and fuzzed (section 10); everything else (report descriptors, SCSI
  answers) is parsed by the class driver, which holds nothing but its own interface. What the
  controller writes back is checked too (section 3).
- **A hostile class driver** can reach only its own interface (section 5), can't program DMA,
  and is cut off when the device goes or it is restarted.
- **The host driver itself** programs DMA, so on Roxy, with no IOMMU, a compromised host driver
  could reach all memory (note 0010, section 6; IOMMU support is M11). That's why it is kept
  small and parses as little as it can.

### 9. Not in M7

- **USB 3 (xHCI)**: M11, with NVMe (ROADMAP.md). Most machines since about 2015 have only xHCI,
  so until then USB works on Roxy and in QEMU, but not on Harriet or Impala.
- **Companion controllers** (UHCI, OHCI), for USB 1.1 devices on older machines: when a machine
  needs it.
- **Isochronous transfers** (audio, cameras): with the audio work (M13).
- **Choosing among configurations**, **alternate settings** (`SET_INTERFACE`), interface
  association descriptors (several interfaces as one function), class and vendor requests to
  the device as a whole: when a class driver needs them.
- **Power**: suspending idle devices, waking the machine from USB, checking a device's power
  needs against what a bus-powered hub can give.
- **Full periodic bandwidth accounting** (section 3), and resetting a device on a class
  driver's request.

### 10. Testing

**On the host** (`cargo xtask test`), in `lib/usb`:
- **Descriptors**: recorded ones from QEMU's devices and from real keyboards, mice, sticks and
  hubs (Roxy's, if Chris copies them, below), plus random corruption of each: every one parses
  or fails cleanly, with no panic.
- **The EHCI structures**: queue heads and transfer descriptors encoded field by field,
  including split transactions' hub, port and masks, checked against values worked out from
  the EHCI specification; the pools' "free only after the doorbell or frame" rule.
- **Hubs and finding devices, against a simulated bus**: a small model in the tests of devices
  and hubs (high-speed hubs with single and multiple transaction translators, low- and
  full-speed devices behind them, hubs five deep) that answers like real ones, including
  devices that lie, stall, never answer, disconnect half-way through being found, and a 128th
  device. This matters because **QEMU can't test hubs or split transactions**: its only hub is
  a USB 1.1 one, which can't sit on an EHCI controller without companions. Roxy is the first
  hardware to run that path for real.
- **The rules of `pbr.usb`** (section 5) as a function from (interface, request) to allowed or
  not, with every recipient and request kind.

**In QEMU** (note 0031 settles which configurations; the plan's Q8 puts EHCI in two):
- QEMU's EHCI with no companions (`ich9-usb-ehci1`, like Roxy's), with its keyboard, tablet and
  stick attached as **high-speed** devices, which QEMU's models can be (stage 4 checks each one
  attaches without a companion). A selftest boot finds them,
  lists them with their paths and serial numbers (unclaimed until note 0030's drivers exist),
  and checks a test class driver's `pbr.usb` calls, including the refused ones.
- **Coming and going**: the test runner plugs a keyboard in and pulls it out with QEMU's
  `device_add` and `device_del` (over QMP, as it already takes screenshots), and the self-test
  checks the device appears, gets its class driver, and goes, with `watch` signalled each time.
- **Crashing**: the host driver is crashed (`pbr.driver.debug`, note 0012) while a test class
  driver is using a device: the device keeps its id and its class driver, `reconnect` answers,
  and the test's next call succeeds; a device pulled out during the restart (`device_del`) is
  gone 10 seconds later.

**On Roxy** (stages 4 and 5, with the serial log): the hand-over from the firmware; both
controllers and their rate-matching hubs; the keyboard and mouse behind them through split
transactions; plugging and unplugging; an external hub if one is to hand.

## Alternatives considered

- **One program for all of USB**, class drivers included. Simpler, but every keyboard's and
  stick's answers would be parsed next to the DMA engine (Q3).
- **Hubs in a class driver of their own.** Section 1: it would need a privileged interface into
  the host driver for addresses, address 0 and the transaction translators, for little gain.
- **Class drivers programming transfers into shared DMA memory.** Faster for storage, but it
  gives every class driver the means to point the controller at any memory; copying costs
  little at USB 2 speeds. Worth revisiting for xHCI and USB 3 sticks (M11).
- **A ring of reports instead of `interrupt_in` calls.** One call per report is fine at a
  keyboard's or mouse's rate (at most 1000 a second), and a ring is a second mechanism to get
  right. If profiling says otherwise, a ring can be added as a new operation.
- **The host driver taking the controller from the firmware itself.** Too late: the device
  manager has switched the controller off by then, under the firmware's feet (section 2).
- **Treating a host driver restart as unplugging everything.** Simpler, but it would take the
  system stick away with it, and every keyboard and mouse would be closed and opened again by
  the input service.
- **Calls from the host driver to the device manager** for each change. Two programs that each
  call the other can each end up waiting for the other; with changes collected by the device
  manager, calls go one way.
- **Keeping `pbr.devices` version 1** and adding operations beside it. Its enums aren't
  flexible and `DeviceInfo` can't grow, so a new device state, a class for host drivers and the
  paths would need a parallel set of everything.

## Open questions

- **Roxy's own USB descriptors** for the host tests: on Roxy's Linux,
  `/sys/bus/usb/devices/*/descriptors` holds each device's raw descriptors, readable without
  `sudo`. Useful for this note and note 0030 (a keyboard's report descriptor is beside it);
  not required.
- Choosing a configuration other than the first, alternate settings, and device-wide class
  and vendor requests (section 9): when a driver needs them.
- Power budgets on bus-powered hubs, and suspending idle devices (M11, with laptops).
- Whether storage needs zero-copy transfers once USB 3 arrives (M11).
